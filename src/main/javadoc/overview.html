Domain Repository 3: repositories which create, provide and track the entities of an application, and Units of Work which write their changes to a storage. The storage is accessed through a DAO (Data Access Object) of the {@code dao4} library, which stores each entity as a data object.

Requirements

  • Java 8 or later. No framework is needed; with Spring (any version), see Using Spring.
  • {@code dao4} (group {@code com.schoste.ddd.infrastructure}), which this artifact brings along, and one of its storages: {@code dao4-fs-serialization} (files), {@code dao4-hibernate} (Hibernate 5.6) or {@code dao4-hibernate-jakarta} (Hibernate 6.6 and later). Version 3.0.0 is built and tested with {@code dao4} 4.1.0.
  • The artifacts are published to GitHub Packages; how to get them, the changelog and the migration from {@code domain-repository} 1.x/2.x (package {@code com.schoste.ddd.domain.v1}): see the README of github.com/phisch84/domain-repository.
  • The test jar of this artifact contains the library's own tests; it isn't meant to be used by applications.

Where to start

  • Using a repository: {@link com.schoste.ddd.domain.v3.services.GenericRepository}. Its class documentation lists the rules which hold for every repository: the cache of entity instances, pending removals, refreshing, and exceptions.
  • Committing changes: {@link com.schoste.ddd.domain.v3.services.UnitOfWork} and its implementation {@link com.schoste.ddd.domain.v3.services.standard.UnitOfWorkImpl}.
  • Atomic commits: {@link com.schoste.ddd.domain.v3.services.DomainTransactionManager} and its implementation {@link com.schoste.ddd.domain.v3.services.standard.DomainTransactionManagerImpl}.
  • Writing entities: {@link com.schoste.ddd.domain.v3.entities.BasicEntity}, the states in {@link com.schoste.ddd.domain.v3.entities.Entity.State}, and {@link com.schoste.ddd.domain.v3.annotations.AutoSet} for the properties which the repository sets from data objects.
  • Writing a repository: {@link com.schoste.ddd.domain.v3.services.standard.GenericRepositoryImpl}. An implementation only provides its DAO; everything else has a default which can be overridden (e.g. to use Spring).
  • Exceptions: {@link com.schoste.ddd.domain.v3.exceptions}.

Rules in brief

  • Repositories never write to the storage; a Unit of Work writes the recorded changes on commit. A commit is atomic only with a transaction manager.
  • The state of an entity tells what happens on commit: Detached, Added, Unchanged, Modified, Deleted. Only the repository sets it: tell it about changes with {@code add}, {@code setModified} and {@code remove}.
  • As long as an entity is referenced, the repository provides the same instance; the cache takes precedence over the storage.
  • Entities are only equal to themselves; compare them by id with {@link com.schoste.ddd.domain.v3.entities.Entity#isSameEntityAs(com.schoste.ddd.domain.v3.entities.Entity)}.
  • An entity whose data object is flagged deleted or missing isn't provided.
  • Streams returned by repositories are lazy and must be closed.
  • Closing a Unit of Work rolls back what hasn't been committed; a rollback makes the repositories forget the changed entities (they become Detached; getting them again loads new instances from the storage).
  • Null arguments are rejected with {@link java.lang.IllegalArgumentException}.

Example

A repository for the entity {@code Customer}, whose data object {@code CustomerDO} is stored by a DAO of the {@code dao4} library, and its use. Spring isn't needed; all objects are created with {@code new}. Note the two {@code AutoSet} annotations: the one of this library on the entity, the one of {@code dao4} on the data object.

import com.schoste.ddd.domain.v3.annotations.AutoSet;
import com.schoste.ddd.domain.v3.entities.BasicEntity;

public class Customer extends BasicEntity<Long>
{
    private String name;

    public String getName() { return this.name; }

    @AutoSet   // set from CustomerDO.getName()
    public void setName(String name) { this.name = name; }
}

import com.schoste.ddd.infrastructure.dao.v4.annotations.AutoSet;
import com.schoste.ddd.infrastructure.dao.v4.models.DataObject;

public class CustomerDO extends DataObject<Long>
{
    private static final long serialVersionUID = 1L;

    private String name;

    public String getName() { return this.name; }

    @AutoSet   // set from Customer.getName()
    public void setName(String name) { this.name = name; }
}

import com.schoste.ddd.domain.v3.services.standard.GenericRepositoryImpl;
import com.schoste.ddd.infrastructure.dao.v4.services.DAO;

public class CustomerRepository extends GenericRepositoryImpl<Long, Customer, CustomerDO>
{
    private final DAO<Long, CustomerDO> dao;

    public CustomerRepository(DAO<Long, CustomerDO> dao) { this.dao = dao; }

    @Override
    protected DAO<Long, CustomerDO> getDataAccessObject() { return this.dao; }
}

// the DAO comes from a storage artifact of dao4 (see the package documentation of its storages)
CustomerRepository customers = new CustomerRepository(customerDAO);

try (UnitOfWorkImpl unitOfWork = new UnitOfWorkImpl(customers))
{
    Customer customer = customers.createEntity();   // Detached, virtual id
    customer.setName("Example Ltd.");

    customers.add(customer);                         // Added
    unitOfWork.commit();                             // saved: actual id, Unchanged

    customer.setName("Example Inc.");
    customers.setModified(customer);                 // without it, the change isn't saved
    unitOfWork.commit();
}

try (Stream<Customer> all = customers.getAll(false))   // streams must be closed
{
    all.forEach(c -> System.out.println(c.getName()));
}

Transactions

Without a transaction manager, a commit which fails part-way leaves the changes written so far written. With one, a commit stores all of its changes or none, and several commits can form one transaction (e.g. when a child needs the actual id of its parent). The storage must support transactions: the Hibernate DAOs of {@code dao4} do, the file DAOs don't.

DomainTransactionManager transactions = new DomainTransactionManagerImpl(new HibernateDAOTransactionManager(sessionFactory));

try (UnitOfWorkImpl unitOfWork = new UnitOfWorkImpl(Arrays.asList(customers, orders), transactions);
     DomainTransaction transaction = transactions.begin())
{
    customers.add(customer);
    unitOfWork.commit();          // customer gets its actual id; joins the transaction

    order.setCustomerId(customer.getId());
    orders.add(order);
    unitOfWork.commit();

    transaction.commit();         // stores both commits; without it, closing rolls both back
}

Using Spring

Repositories, Units of Work and transaction managers can be Spring beans like any other object. Override the two hooks of {@link com.schoste.ddd.domain.v3.services.standard.GenericRepositoryImpl} only if entities, or the classes named by {@code @AutoSet(clazz = ...)}, must be created by Spring:

public class SpringCustomerRepository extends GenericRepositoryImpl<Long, Customer, CustomerDO>
{
    @Autowired private ApplicationContext context;
    @Autowired private DAO<Long, CustomerDO> dao;
    private AutoObjectConverter converter;

    @Override
    protected DAO<Long, CustomerDO> getDataAccessObject() { return this.dao; }

    // only if entities are Spring beans (e.g. prototype beans with injected services)
    @Override
    protected Customer doCreateEntity(Class<Customer> entityClass, Object... args)
    {
        return this.context.getBean(entityClass, args);
    }

    // only if classes named by @AutoSet(clazz = ...) are Spring beans
    @Override
    protected synchronized AutoObjectConverter getAutoObjectConverter()
    {
        if (this.converter == null) this.converter = new AutoObjectConverterImpl()
        {
            @Override
            protected Object getInstance(Class<?> clazz) { return context.getBean(clazz); }
        };

        return this.converter;
    }
}

Common mistakes

  • Changing an entity without {@code setModified}: the change is only in memory; the next commit doesn't save it.
  • Expecting a repository method to write: {@code add}, {@code setModified} and {@code remove} only record; nothing is stored until a Unit of Work commits.
  • Keeping the id of a new entity before the commit: it is virtual and replaced by the actual id on commit; read the id after the commit.
  • Comparing entities with {@code equals} or by id in {@code equals}/{@code hashCode}: use {@code isSameEntityAs}; an id-based {@code hashCode} breaks the repository's collections when the id changes on commit.
  • Not closing streams: the DAO keeps its resources (e.g. a database session) open until the stream is closed.
  • Setting the state of an entity yourself: registers nothing; use the repository's methods.
  • Using an entity after a rollback: the repository has forgotten it (Detached); get it again for the stored state.
  • Several Units of Work on one repository at the same time: each of them records all changes of the repository; use one Unit of Work per repository at a time.
  • Expecting atomic commits without a transaction manager, or with a storage which doesn't support transactions.
